# Assumptions & Design Decisions

Decisions made where the brief was silent or ambiguous, and why.

## Scope

1. **Missing brief sections.** Sections 1–4 and 6 of the brief were not available. They are
   assumed to cover project setup, the Accounts API and the Transactions API (create and list).
2. **Authentication and authorisation are out of scope.** Every endpoint is public. The
   OpenAPI document declares this explicitly (`security: []`).
3. **Single currency.** The system holds one currency. The frontend displays it as INR by
   default (configurable with `VITE_CURRENCY`); the API itself is currency-agnostic.

## Money

4. **Minor units.** Amounts and balances are stored as `BIGINT` minor units (paise/cents).
   Conversion is string-based, so `0.1 + 0.2` is exactly `0.30`; no floating-point
   arithmetic touches money anywhere in the stack.
5. **Input format.** `amount` may be a JSON number (`30.5`) or a numeric string (`"30.50"`),
   must be greater than 0, and may have at most 2 decimal places. Strings are recommended for
   clients that cannot represent decimals exactly.
6. **Output format.** Money is always returned as a 2-decimal string (`"100.00"`), never a
   number, so no client parses it into a float by accident.
7. **Upper bound.** A single transaction or transfer is capped at `1,000,000,000.00`. This
   keeps every balance far below the `BIGINT` ceiling.

## Accounts

8. **Opening balance is always 0.** Funds arrive only through credit transactions or
   transfers. Unknown request fields are rejected, so `{"balance": 1000}` on create is a
   `400`, not silently ignored.
9. **Accounts are permanent.** There are no update or delete endpoints (they return `405`);
   foreign keys use `ON DELETE RESTRICT`. Deleting an account would orphan or erase ledger
   history.
10. **Names** are trimmed and must be 1–100 characters. Names need not be unique.

## Transactions

11. **Immutable ledger.** Transactions are append-only. The API returns `405` for
    `PUT`/`PATCH`/`DELETE`, and a database trigger rejects `UPDATE`/`DELETE` on the
    `transactions` and `transfers` tables even from direct SQL. `TRUNCATE` is deliberately not
    blocked, so test suites and administrators can still reset an environment.
12. **`reference_id` semantics.** Required, trimmed, 1–64 characters, case-sensitive.
    - Unique **per account**: a duplicate on the same account is rejected with `409`.
    - The same reference **may** be used on different accounts.
    - A duplicate is rejected rather than replaying the original response. The caller can
      look up the existing transaction if it needs the result.
13. **No negative balances.** A debit larger than the balance is rejected with `422`.
    The check runs under a row lock, and a `CHECK (balance >= 0)` constraint is the final
    safety net.
14. **Description** is optional, trimmed, at most 255 characters; an empty string is stored as
    `null`.

## Transfers (bonus)

15. **Representation.** A transfer is one `transfers` row plus two immutable ledger entries: a
    debit on the source and a credit on the destination, both linked by `transfer_id`. Both
    appear in the respective account histories.
16. **Transfer references** are globally unique across transfers. Both ledger entries carry
    the transfer's reference, so it must also be unused by any transaction on either account.
17. **Same-account transfers** are rejected with `400 SAME_ACCOUNT_TRANSFER`. Account ids are
    compared case-insensitively, matching how PostgreSQL treats UUIDs.
18. **Deadlock avoidance.** Both accounts are locked in ascending id order, so concurrent
    opposite-direction transfers (A→B and B→A) queue instead of deadlocking.

## Listing & pagination

19. **Ordering.** Transactions are listed latest first, by `created_at DESC, id DESC`. The id
    tie-breaker keeps page boundaries stable when rows share a timestamp. Accounts are
    listed newest first in the same way.
20. **Pagination.** `page` defaults to 1 and `limit` to 10 (maximum 100). Values that are not
    integers, are below 1 or exceed the maximum return `400 INVALID_PAGINATION`. A page past
    the end returns an empty list with correct `meta`, not an error.
21. **Unknown account** on the history endpoint is a `404`, not an empty list.

## API conventions

22. **Timestamps** are stored as `timestamptz` and returned in UTC ISO 8601.
23. **IDs** are UUIDs generated by PostgreSQL (`gen_random_uuid()`).
24. **Request tracing.** Every response has an `X-Request-Id`. A well-formed incoming id
    (letters, digits, `_`, `-`; max 128 characters) is reused, so callers can correlate logs.
25. **Error details** are only exposed for client errors. Unexpected failures return a generic
    `500` and are logged server-side with the request id.

## Frontend

26. **Account pickers** on the transfer screen load the first 100 accounts (the API's maximum
    page size), which is ample for this application.
27. **Client-generated references.** Forms pre-fill a random `reference_id` once per form, so
    a retried or double-clicked submission re-sends the same reference and cannot move money
    twice.
